### D3. Where access is enforced. This is the most important decision.

**The core problem:** row-level security (RLS) decides which rows a user can read, not which columns. Two things here are column problems:
- **Home location:** members need each other's `display_name` for attendee lists, but `home_lat` and `home_lng` are in the same row.
- **The exact meeting point:** a member can see a meetup row, but must not see its coordinates or place name until they RSVP.

**What I'd propose:**

1. **Split the secret into its own table.** Use `meetups` for the public part (title, time, status, approximate area) and `meetup_meeting_points` for the exact name and coordinates. The meeting-point table gets its own RLS rule: you can read a row only if you are the creator or have RSVP'd.
   - The column problem becomes a row problem, which RLS handles well.
   - The map updates after RSVP automatically, because the next read returns the row.
2. **Home location: column-level grants plus RLS.** `authenticated` gets `SELECT (id, display_name)` on `users` and nothing else. Asking for `home_lat` then fails with a permission error for everyone. On top of that, an RLS rule limits rows to people who share a group with you.

## D3 explained

### Step 1: what Supabase exposes

`supabase start` gives you Postgres plus an automatic API called PostgREST. **Every table in the `public` schema becomes an API endpoint.** Anyone holding your anon key, which ships inside the app, can send queries like:

```
GET /rest/v1/meetups?select=*
GET /rest/v1/users?select=display_name,home_lat,home_lng
```

So "the app doesn't request that column" protects nothing. Someone can pull the key out of the app and query any table directly. **The database itself has to refuse.**

Each request runs as one of three Postgres roles:

| Role | Who | In our design |
|---|---|---|
| `anon` | no sign-in | gets nothing |
| `authenticated` | a signed-in user. `auth.uid()` returns their id. | reads only, filtered |
| `service_role` | server-side code with the secret key; bypasses RLS | only our Edge Functions |

### Step 2: two separate locks

Postgres checks two things on every query, and both must pass:

1. **GRANT** decides whether a role may touch a **table or column** at all. Example: `grant select (id, display_name) on users to authenticated`.
2. **RLS policy** decides **which rows** that role sees. Example: `using (is_group_member(group_id))`.

> **The important limit:** RLS filters rows. It can't show a row with some columns blanked out for some people. If Sam can see a row, he can see every column he has a GRANT for.

Both of our privacy rules are about hiding *parts* of a row. That's why plain RLS isn't enough here.

### Step 3: the meeting point

Suppose we do the obvious thing:

```sql
create table meetups (..., meeting_point_name text, meeting_point_lat float, ...);
create policy "members read" on meetups for select using (is_group_member(group_id));
```

Sam is a member who hasn't RSVP'd. He runs:

```
GET /rest/v1/meetups?select=meeting_point_name,meeting_point_lat
→ "North gate, Linden Park", 40.012046   ❌ leaked
```

The policy let him see the row, so he gets every column in it. There are three ways to fix this:

| Option | How | Problem |
|---|---|---|
| A. A "security definer" view with `CASE WHEN rsvp'd THEN lat ELSE null` | The view runs with the owner's rights and decides per row | It **bypasses RLS**. A missed `WHERE` clause leaks everything, and Supabase's linter flags this pattern. |
| B. Reads only through endpoints or functions | Hand-written read functions | More code; every read path is a new place to get it wrong |
| **C. Split the table** ✅ | Move the secret columns into their own table, which has its own policy | None significant |

**Option C:**

```
meetups                              meetup_meeting_points
─────────────────────                ─────────────────────
id, group_id, created_by             meetup_id  (PK, FK)
title, starts_at, status             name
area_lat, area_lng, area_radius_m    lat, lng
  ↑ approximate, computed once
RLS: is_group_member(group_id)       RLS: is_creator(meetup_id) OR has_rsvp(meetup_id)
```

Now Sam's query on `meetup_meeting_points` returns **zero rows**. The hidden-columns problem has become a hidden-row problem, and RLS handles that well. Two more things follow from this:
- **The map updates after RSVP by itself.** The next query returns the row, with no special code.
- **The rule is one line of SQL** that a reviewer can read and our tests can prove.

The app reads through a view, `meetup_details`, that joins the two tables. The view is created with `security_invoker = true`, so it runs **as the user** and RLS still applies. When the meeting-point row is hidden, the joined columns come back null. The shared Zod schema then turns the result into either `{kind:"exact", name, lat, lng}` or `{kind:"approximate", lat, lng, radius_m}`.

### Step 4: home location

The attendee list needs other people's `display_name`, so members must be able to read some of `users`. The same trap applies: if Sam can see Avery's row, he can request `home_lat`.

Here we use a column GRANT instead of splitting the table. We're told not to reshape the starter tables heavily, and this case allows it:

```sql
revoke all on public.users from anon, authenticated;
grant select (id, display_name) on public.users to authenticated;
create policy "see co-members" on public.users for select
  using (shares_a_group_with(id));
```

Now `select=home_lat` fails with **permission denied** for every user, including on their own row, because no feature in this slice needs it. A view or join that tries to pull it in fails the same way. Tests will check this for every persona.

> Pushback note: the real fix is to move private fields into a separate `user_private` table that has no grants at all. Keeping a "never expose this" column next to public profile data invites a leak. That's a good item for your note.

### Step 5: writes

The spec says every write must go through Zod validation on the server, and that "a write sent from the app straight to a table or a Postgres function does not meet the requirement." So we have to make the bypass **impossible**, not just discouraged:

```
App ──POST /functions/v1/rsvp {meetupId}──▶ Edge Function
                                             1. verify JWT → userId (never from body)
                                             2. Zod: RsvpInput.parse(body) → 400 if bad
                                             3. call rpc('rsvp', {user_id, meetup_id})
                                                as service_role
                                                         │
                                                         ▼
                                           Postgres function rsvp()
                                             - is user a member of the group?
                                             - status = 'scheduled'?
                                             - starts_at > now()?
                                             - insert ... on conflict do nothing
                                               (idempotent: RSVPing twice is fine)
```

And in the database:
- `authenticated` gets **no** INSERT, UPDATE or DELETE on any table.
- `execute` on the write functions is **revoked** from `authenticated` and granted only to `service_role`.
- So if the app tries `POST /rest/v1/rsvps` or `/rpc/rsvp` directly, it's denied. Tests will prove that too.

**Why rules live in both places:** each layer covers something the other can't.

| Layer | What it's good at |
|---|---|
| Zod (the Edge Function) | Shape, lengths, ranges, the "start time is in the future" rule, clear error messages. The schema is shared with the app, so the form gets the same validation. |
| Postgres function | Rules that need data (membership, creator, cancelled, started). They run in one transaction, so they can't race, and no client can skip them. |

**The cost of this design:** the Edge Function holds the service-role key and passes the user id along itself. A bug in that function could act as the wrong user. We keep that risk small: the user id comes only from the verified JWT, there's one shared helper for it, and tests cover it. The alternative is letting users call the functions directly with their own session, which is what the spec rules out. Say this tradeoff in the recording; it's the kind of thing reviewers listen for.

### Step 6: a problem you'll hit

The policy on `meetups` checks `group_memberships`, and the policy on `group_memberships` also needs to check membership. Policies that query each other this way can loop forever ("infinite recursion detected in policy").

The standard fix is small `security definer` helper functions, such as `is_group_member(gid)` and `has_rsvp(mid)`:
- They run with the owner's rights, read the membership table directly, and return only true or false.
- They're safe because a yes/no answer doesn't leak data.

### Everything at a glance

| Rule | Enforced by |
|---|---|
| Outsiders see nothing | RLS: `is_group_member` on meetups, RSVPs, meeting points and users |
| Exact point only for the creator or attendees | A separate table with an RLS rule for creator or RSVP |
| Approximate area not centered on the exact point | Computed once at creation and stored in `meetups.area_*` |
| Home location never exposed | Column GRANT (and no endpoint ever selects it) |
| Only the creator cancels; cancelling is final | `cancel_meetup()` checks the creator and the status |
| No RSVP once cancelled or started | `rsvp()` checks both |
| Every write is Zod-validated | No write grants for users; functions callable by the service role only |

## My recommendation: your phone over USB, mirrored with scrcpy

I'd have suggested the emulator earlier, but on this machine the phone is the better choice:

| | Emulator | **Phone + USB + scrcpy** ✅ |
|---|---|---|
| Download | Android Studio, about 4 GB or more | scrcpy, about 10 MB (it includes `adb`, the Android device tool) |
| RAM | 2–4 GB more. Docker already has about 7.4 GB of your 15 GB, so with VS Code, the browser and the recorder it gets tight, and a lagging recording looks bad. | Almost nothing; the app runs on the phone |
| Networking | Simple (`10.0.2.2`) | Simple. A USB "reverse" tunnel lets the phone use `127.0.0.1`, with no Wi-Fi or firewall setup. |
| On screen | Emulator window | The scrcpy window mirrors your phone live, and `--show-touches` shows your taps |

USB is also more reliable than Wi-Fi. Over Wi-Fi, the phone has to reach your PC at `192.168.100.23`, which means Windows Firewall rules, a network marked Private, and a router that allows device-to-device traffic. Any of those can fail in the middle of a recording.

---

## Setup (about 15 minutes)

### 1. Phone
1. Install **Expo Go** from the Play Store.
2. Turn on **Developer options**: Settings → About phone → tap **Build number** 7 times.
3. In Developer options, turn on **USB debugging**.
4. Connect the phone to your PC with a USB cable that carries data, not just charge. When it asks **"Allow USB debugging?"**, tap Allow.

### 2. scrcpy on the PC
1. Download the latest `scrcpy-win64-vX.Y.zip` from https://github.com/Genymobile/scrcpy/releases.
2. Unzip it to `C:\tools\scrcpy`.
3. Add that folder to your **user PATH**: Start → "Edit environment variables for your account" → Path → New → `C:\tools\scrcpy`.
4. **Restart VS Code** so its terminals pick up the new PATH.
5. Check it works:
   ```
   adb devices
   ```
   You should see one device listed as `device`. If it says `unauthorized`, accept the prompt on the phone.

### 3. Point the phone at your PC over USB
Run this each time you plug the phone in:
```
adb reverse tcp:54321 tcp:54321
adb reverse tcp:8081 tcp:8081
```
The first line forwards Supabase (API, Auth and the endpoint). The second forwards the Metro bundler, which serves the app's code. On the phone, `127.0.0.1` now means your PC.

Then edit `apps/mobile/.env` (it isn't committed) and change the URL line:
```
EXPO_PUBLIC_SUPABASE_URL=http://127.0.0.1:54321
```

### 4. Run the app
In your own terminal:
```
cd apps\mobile
npx expo start --localhost --clear
```
Press **`a`**. Expo finds the phone through `adb` and opens the app in Expo Go. `--clear` makes sure the new `.env` value is used, because Expo bakes environment values into the bundle.

### 5. Mirror it
In a second terminal:
```
scrcpy --show-touches --stay-awake --max-size 1080 --window-title "Altair (Android)"
```
- `--show-touches` draws a dot wherever you tap, which helps viewers follow along.
- `--stay-awake` keeps the phone screen from sleeping mid-recording.

2. **The future-start rule applies only when the start time actually changes.** So the creator can still fix a typo in the title of a meetup that has started. The spec is silent on that case, so it goes into the assumptions.
3. **Moving the meeting point gets a new approximate area.** Otherwise the old circle might not even contain the new spot. But it's regenerated **only if the coordinates really change**. Re-saving the same point must not produce a fresh random circle, because collecting enough circles around one point and averaging them would reveal the exact spot.
4. **Existing RSVPs are kept** when the time or place changes. Telling attendees about the change needs notifications, which the spec puts out of scope. That goes in your pushback list.
5. **Access works the same way as the other writes:**
   - App users have no UPDATE permission on the tables.
   - The new database function can only be called with the server's service-role key.
   - Cancelled meetups are already locked by a database trigger, so even an edit sent straight to the database is blocked.
